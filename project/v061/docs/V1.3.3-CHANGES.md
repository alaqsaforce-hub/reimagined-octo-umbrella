# VoiceDock AI v1.3.3 — the accessibility pass: silent send, and the transcript panel

Release date: 2026-11-01 · versionCode 25 · versionName "1.3.3" · minSdk 26 · target/compile 35

Two promises from earlier releases were written with a caveat attached. This release removes both caveats, and
keeps every limit that remains honest.

## 1. Sending without a live notification (`send/SendCore.kt`, `send/AccessibilitySender.kt`)

Until v1.3.2 a message was really sent only when the app offered a Direct Reply action on its notification
(v0.8), or when a scheduled message could open the chat pre-filled (v1.2.1). The third route is now real:
**type into the chat that is already open and press the app's own Send button**, through accessibility.

This is the one feature where a mistake is visible to another person, so the guards are strict and pure:

* The app in front must own the field: `expectedPackage` mismatch → **WRONG_APP**, and nothing is typed.
* The field must look like a **message box**, not a search box (`looksLikeMessageField` rejects anything whose
  hint/id says "search" — typing a message into a search bar is worse than refusing).
* A send button must actually exist. Labels are matched across the languages these apps ship
  (Send / পাঠান / Enviar / Senden / Envoyer / 送信 / Отправить / إرسال …), and only "Send now / Send message /
  Send reply" may follow the word — **"Send location" is not a send button** (a test enforces it).
* Password/secure fields, finance-labelled apps and secret-looking text are refused (`SECURE_FIELD`).
* **"Sent" is claimed only when the composer really emptied after the click.** Anything else returns
  `REJECTED` / `NO_SEND_BUTTON` …, the text is put on the clipboard, and the bubble says what stopped it and
  tells the user to paste and send by hand.
* Nothing is ever sent automatically: the route runs from a spoken "রহিমকে বলো …" (or a scheduled message) and
  the outcome is the message the user sees.

Where it hooks in: `MSG_REPLY` — when the app has no live notification or no reply action, the accessibility
route is tried **once**, and the failure text is the union of both honest reasons.

## 2. Reading the transcript of the video that is open (`summaries/ScreenTranscript.kt`)

v1.3.2 could read a video's title and description and said captions could not be read. Now they can — **from the
panel the user opened**:

* new intent **`yt.transcript`** — "ট্রান্সক্রিপ্ট পড়ে সারমর্ম দাও", "স্ক্রিনের ভিডিওর সারমর্ম বলো",
  "summarise the captions";
* the screen text of the YouTube app is cleaned: timestamps stripped, panel chrome
  (Show transcript / Subscribe / Like / Home …) and duplicates dropped, capped at 60 lines / 6,000 characters;
* confidence comes from evidence — a transcript label **or** 5+ timestamp-only lines — so an ordinary screen is
  never "summarised" as a video;
* with an AI provider the cleaned lines are summarised (prompt: *never add anything not in the transcript*);
  without one, the lines themselves are shown. The answer is labelled **"📝 স্ক্রিনের ট্রান্সক্রিপ্ট থেকে"**;
* if the panel is not on screen the answer is **instructions**, not a guess: open the video, tap "…", turn on
  *Show transcript*, ask again. If the panel is open but empty, it says the video has no captions.

Nothing taps around inside YouTube on its own: the user opens the panel, the assistant reads it.

## What is still not done (and is still said in the app)

* The accessibility route depends on each app's own node tree; the code reports every failure instead of
  pretending, and no WhatsApp/Instagram API is used or assumed.
* **Calendar read/add** is not in this build (it needs the Google OAuth REST path); it stays the next item.
* Group-chat "which conversation is open" is not detected — the route only types when the app in front matches
  the chat app and the composer proves itself.
